# Render Deployment — Portmetals Africa

One-command production deployment on Render (free tier). The server is a single
Node process: it serves the built React app **and** the API (AI chat, quote
analyst, finance agents, Twilio calling, cloud sync).

## 1. Create the service

**Option A — Blueprint (recommended):**

1. Push this repo to GitHub and connect it.
2. On Render → **New → Blueprint** → pick the repo. Render reads `render.yaml`
   and provisions the `portmetals-africa` web service with the build/start
   commands, health check, and the generated sync secret.
3. Click **Apply**.

**Option B — Manual:**

- **New → Web Service** → pick the repo.
- Build command: `npm ci && npm run build`
- Start command: `npm run start`
- Health check path: `/api/health`
- Plan: Free.

Then add the env vars from the table below.

## 2. Environment variables

| Variable | Required | Where to get it |
| --- | --- | --- |
| `VITE_SYNC_DEVICE_SECRET` | **yes** | Auto-generated by the blueprint (`generateValue`). Keep it. |
| `HUGGINGFACE_API_KEY` | **yes** | **Primary AI** — HF Access Token (https://huggingface.co/settings/tokens) with Inference enabled. |
| `HUGGINGFACE_MODEL` | no | `meta-llama/Llama-3.3-70B-Instruct` (default) — any model on HF Inference Providers. |
| `GEMINI_API_KEY` | no | https://aistudio.google.com/apikey — powers the copilot voice (TTS) and the fallback chat provider. |
| `SUPABASE_URL` | no* | Supabase → Project Settings → API → Project URL. |
| `SUPABASE_SERVICE_ROLE_KEY` | no* | Supabase → Project Settings → API → `service_role` (server only). |
| `OLLAMA_ENABLED` | no | `"true"` to use your self-hosted Qwen3 VPS as the primary AI. |
| `OLLAMA_BASE_URL` | no | Your VPS Ollama endpoint, e.g. `http://<VPS-IP>:11434/v1` (via SSH tunnel / reverse proxy — don't expose the port publicly). |
| `OLLAMA_MODEL` | no | `qwen3:4b` (default). |
| `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` | no | Twilio Console — enables live AI calling. |
| `TWILIO_PHONE_NUMBER` | no | Your Twilio voice number (E.164). |
| `TWILIO_TWIML_BASE_URL` | no | `https://<your-app>.onrender.com` — where Twilio fetches call scripts. |
| `FLUTTERWAVE_SECRET_KEY` | no* | Flutterwave dashboard → Settings → API. **Enables live payments.** |
| `FLUTTERWAVE_SECRET_HASH` | no* | `openssl rand -hex 16` — set the same value in Flutterwave → Webhooks → Webhook Hash. |

\* Without Supabase the app runs fully offline (localStorage), exactly as in
dev. Add Supabase when you want cloud state sync (see `deploy/SUPABASE.md`).

\* Without Flutterwave keys the entire payments flow runs in **local simulation
mode** — checkout, simulate pay/decline, status polling and bank withdrawals all
work locally with no keys. Set the two keys to go live (see `deploy/PAYMENTS.md`).

`PORT` and `NODE_ENV` are set automatically by Render.

## 3. Cloud sync (optional)

Run `deploy/supabase/schema.sql` once in the Supabase SQL Editor, then add
`SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`. The sync API requires the device
secret header, which is auto-generated and shared automatically — you don't
need to do anything else.

## 4. After deploy

- The app listens on Render's `PORT` at `https://<your-app>.onrender.com`.
- Health check: `/api/health` returns `{"status":"healthy"}`.
- Unknown `/api/*` routes return a JSON 404 (never the SPA shell).
- Live AI calling: point your Twilio number's voice webhooks at
  `https://<your-app>.onrender.com/api/twilio/inbound` and
  `/api/twilio/status`. Twilio signature validation is on automatically when
  `TWILIO_AUTH_TOKEN` is set.
- Payments: see `deploy/PAYMENTS.md` to switch from simulation to live
  Flutterwave checkout + payouts.

## 5. Updating

Push to `main` → Render redeploys automatically (`autoDeploy: true`). The build
runs `tsc --noEmit` first, so a type error fails the build instead of shipping.
